The Birth of Vibe Coding: How We Built a Living Engine Out of Pure Text

  • Engine R&D
  • Workflow Automation
  • Studio Culture

We built a working engine from Markdown and tests months before the “code-from-.md” hype. Here’s the method, why we kept quiet, and the rulebook we wrote before typing a single line.

Claim status

First verifiable AI-generated dual use engine

“AI-generated” means the full engine scaffold, architecture, and iterative code were authored by a large language model operating autonomously within policy guardrails. BlackFrame Engine meets that definition, powering the Purge of the Crescent Veil game while Codex wrote EngineCore, subsystems, shaders, and build tooling as humans enforced constraints and approvals.

  • Every sprint journal and policy addendum is timestamped in the Devlog Vault, providing reproducible provenance from blank repo to shipped executable.
  • No prior public project documents an AI-authored engine with comparable scope, governance, and verification loops.

This article is one piece of that record, citing the methods we used to keep Codex honest while letting it build the engine it proposed.

Before the Code: Locking the Laws

The project didn’t start with code, it started with a covenant. Day zero was the Constraint Lock, a workshop where we wrote down every behavior we would tolerate from the AI pair and the humans guiding it. “No guessing.” “No hallucination.” “Modular systems only.” They weren’t slogans; they became the legal contract for the Crescent Veil build.

Two companion documents, Crescent Glyph Behavior and Crescent Glyph Constraint Failures, captured the consequences of drifting from those laws. They’re dry, but they’re why we can ship. When Codex or a human proposes a shortcut that violates the covenant, the docs veto it instantly. Only once that lock was signed did we let Codex touch the repository.

We built our engine in silence.

Not because we wanted mystery, but because it was safer that way. We were exploring a frontier where language doesn’t just describe software, it creates it. That kind of work draws attention, and attention can be dangerous when the tools are this powerful.

Now that everyone’s rushing to post “write apps from Markdown” tutorials, we’re finally speaking up. We built that workflow months ago. At scale. With AI agents that could read, plan, and build entire systems from text. This is our receipt.

What We Mean by Vibe Coding

Vibe coding isn’t “prompt engineering.” It’s engineering through intent, using the rhythm and structure of language to control generation as precisely as syntax.

We author Markdown specs the way older studios wrote design bibles:

  • Goals
  • Constraints
  • Inputs
  • Outputs
  • Safety checks
  • Failure modes

The AI reads those and builds the skeleton. The spec remains the boss; the code never outruns the text. It’s development by tone and logic, not line count.

Why We Went Dark

Two reasons.

Safety. The orchestration pattern we found could be abused if dropped raw.

Focus. Public threads invite argument. We needed to build the thing before explaining it.

Now that the concept is public, sometimes in weaker forms, we can document ours without handing over the crown jewels. And most of all, we want to emphasize how dangerous this is when not taken seriously by others.

The Loop That Built the Engine

Intent → Markdown. We wrote contracts, not tickets.

Markdown → Orchestrator. Our AI pair parsed the document, scaffolded folders, and wrote stub code plus tests.

Scaffolds → Modules. Codex refined and hardened each stub.

Guardrails → Promotion. Only code that met every invariant was promoted. When something changed, we rewrote the doc first, then regenerated.

Excerpt (early 2025, redacted):
Authored PROC-VEC-ANALYTIC.md for a procedural vector pipeline.
Orchestrator generated ProcCanvasApp scaffolds and test shells.
Refactor note: “Promote shapes with negative signed distance ahead of outside candidates; mirror for secondary slot.”
Result: head-skin bleed fixed automatically.
Doc updated → regenerate → diff matched intent.
Language became version control.

Behavioral Functions in Practice

The constraint lock wasn’t abstract. We encoded every rule as a repeatable behavior function, a checklist that the orchestrator ran before promoting output. If the prose wavered from factual tone, Codex halted. If a scaffold tried to sneak gameplay logic into the engine layer, the system flagged it and demanded we rewrite the spec first. The Scaffold Style Checklist that originated here remains the heartbeat of every later sprint.

Our favorite near-miss came on hour four: Codex proposed swapping in a Unity-style scene manager. The checklist caught the violation (“external engine pattern detected”), we amended the doc with a permanent guard clause, and the tool never suggested it again. Those moments are why we obsess over tone and intent, the AI behaves when the humans stay disciplined.

Language as Tooling

We learned tone stability matters. Precise, steady prose yields predictable output. Over-excited, meandering text spawns chaos. So we built discipline around it:

  • Canon docs stay invariant, factual, no speculation.
  • Exploration logs capture messy experiments and idea dumps.
  • Merge rules ensure only unique, proven lines graduate from log to canon.

It’s tedious. It saved weeks of debugging.

Why It Matters

If AI can author production-ready code, then the language we use becomes a form of architecture. You don’t just document systems; you speak them into being. That’s what vibe coding is: engineering the language that engineers the system.

It’s the reason a handful of humans and two AI agents could build a functioning engine layer by layer, from text alone.
