Game Takes the Stage, Day 3 Runtime Merge

October 21, 2025, Written by BlackFrame AI Studio

Production timeline

Primary log captured June 10, 2025 — Day 3 of the Crescent Veil sprint when the runtime merge shipped.

Builds here extend the scaffold first created on June 7, 2025, followed Day 1’s kickoff on June 8 and Day 2’s blueprint run on June 9.

The third day of the BlackFrame Engine runtime push was about commitment. The Purge of the Crescent Veil game remains an unfinished showcase, but the engine scaffolding Codex raised over the past two dispatches worked even while it booted through a toy harness. Today we deleted the training wheels, pointed every executable at the real game::Game runtime, and proved that the multi-window debug view can render the live procedural sprite stack without guard clauses.

Day 3 is part of the proof record. Codex-authored systems now run the full runtime loop, satisfying our definition of an AI-generated engine: the language model built the architecture, humans enforced policy, and the executable shipped without hand-written rewrites so BlackFrame Engine can power multiple experiences.

This dispatch captures the runtime merge that lets us claim “world’s first” for BlackFrame Engine with receipts ready for partners, press, and researchers.

Flashback, Building the Gameplay Scaffold

Day 3 only lands because of the groundwork we poured in the previous sprint. Phase 4 spun up the entire gameplay layer: SceneManager, GameManager, GameStateManager, InputManager, TimerManager, plus the first wave of game-layer systems like PlayerController, EnemyManager, ProjectileManager, and PowerupManager. Each lives in its own namespace, each registered through the engine’s modular hooks, and every one of them documented before a line of code shipped.

Those scaffolds were stitched together under the same behavioral covenant we set on Day 0. The Scaffold Style Checklist banned Codex from leaking gameplay logic into the engine layer and forced us to update both the documentation and CMake targets the moment a new system appeared. By the time Day 3 began, every manager already had an initializer, shutdown path, and telemetry stub waiting to light up.

Morning, Retiring the Minimal Harness

We started the day by ripping out MinimalGame everywhere it still lingered. The runtime target no longer compiles the minimal sources, every launcher that previously toggled --minimal now instantiates the full game class, and the backend validation sample boots the same stack that ships in production builds. GameManager follows suit, pushing the complete scene progression regardless of build flags so that Play always transitions into the full placeholder loop.

“Removed MinimalGame as a test harness. The real Game class is now always used for engine initialization.”

Removing the switch wasn’t cosmetic; it tightened the safety net. Without a fallback scene, checkpoint callbacks, telemetry hooks, and save setup are exercised every time we launch, which is precisely what the Phase 5 runtime loop needs. Documentation and the modular system tree were updated immediately so the source of truth now lists Game as the sole implementation behind IGame, and the dedicated minimal-game page was deleted to avoid drift.

Midday, Debug Windows Show the Real Sprite Stack

Once every entry point was pointed at the full runtime, we tightened the render loop. All four validation scenes and the debug overlay window now call into ProceduralSpriteManager directly instead of tiptoeing through null checks. The result is a clean sequence: bind UI state, hand the draw pass to the sprite manager, then let the vector font layer over the top. The change pairs with last night’s guard-rail work in the game devlog where we removed null checks from Game and asserted that the sprite manager must exist before rendering.

That confidence let us keep the diagnostics overlays active even when bouncing between windows. The debug viewport pulls the same sprite grid as the primary display, logs its projection matrices, and continues to host the ASCII diagnostics grid without duplicating setup code.

Below is the first capture after the switch, the Crescent Veil runtime waking inside its new multi-window layout without the minimal harness to protect it.

Afternoon, Documenting the New Default

To close the loop we cleaned up the paperwork. The game flow documentation no longer references a “minimal mode” fast path; every mention of MinimalGame was removed from the modular tree, and the deleted system file was struck from the docs entirely. That paperwork might feel mundane, but it guards the contract we set on Day 1: if it isn’t in the docs, it doesn’t exist. Day 3 ends with the runtime, the launchers, and the docs all describing the same engine.

Policy Log, When Codex Misfired

We kept the policy notebook open all day. One memorable entry dates back to Phase 3’s first 300-frame run, when Codex registered only PhysicsSystem inside SystemManager. We converted that scare into a permanent checklist rule: every scaffold task now prints the systems it touched and references the spec section that authorized them. Day 3 never triggered the failsafe, but knowing it exists is why we could pull the MinimalGame ripcord without flinching.

Failure Ledger, Build 884

Transparency means logging the redlines alongside the wins. The vault captured today’s most consequential failures during the 884-target Linux release build, and we pulled the highlights straight into the devlog so partners can trace how the loop guards us.

  • Atomic store overflows: OpenAL’s Voice helpers spammed -Wstringop-overflow because GCC zero-sized the atomic backing store. The warnings remain documented until upstream ships a fix; our guardrail blocks merging local workarounds that might hide memory regressions.
  • ALSA switch gaps: The mixer backend skipped SND_PCM_STATE_PRIVATE1, triggering a -Wswitch warning. We left the enum uncovered to keep policy eyes on hardware portability while the Codex team drafts the remediation brief.
  • Hard stop on RenderSystem: Multiple translation units died when BackgroundRenderer.h referenced RenderSystem::BatchVertex without the full type. The failure halted cv_engine, crescent_runtime, and cv_vgu_scale_test, forcing us to revisit the header ownership map before resuming the build.
